# แผนดำเนินงานต่อหลัง staging 0.1.29

วันที่ 14 ตุลาคม 2026 — อ้างอิง [แผนความเสถียร](KOKO_STUDIO_STABILITY_PLAN.md) และ [ผลพื้นที่ว่าง 0.1.29](KOKO_STUDIO_STORAGE_2026-10-14.md)

## เป้าหมาย

ทำให้การปิดแอปกะทันหันไม่ทำให้งานพิมพ์ส่งซ้ำเอง และกู้ความสัมพันธ์ระหว่างสื่อที่บันทึกแล้วกับรอบถ่ายได้ จากนั้นตรวจสำรอง/กู้คืนและจัด candidate ใหม่สำหรับทดสอบจริง งานระยะ 2–3 ยังไม่ผ่านทั้งหมด

## ผลตรวจตั้งต้นและสิ่งที่ลงมือแล้ว

เพิ่ม `scripts/studio-desktop-reliability-check.cjs` ใน repo เว็บเพื่อเรียก storage services ของ Desktop ด้วยข้อมูลสังเคราะห์ในโฟลเดอร์ชั่วคราว สคริปต์สร้าง process แยก รอจุดบันทึกที่กำหนด แล้วหยุดเฉพาะ process ที่สร้างเอง ก่อนเปิด store ใหม่เพื่อตรวจข้อมูล ไม่เรียกเครื่องพิมพ์ ไม่เปิดแอปจริง และไม่อ่านรูปหรือ app data ของผู้ใช้

| จุดหยุด process | ผลก่อนแก้ | ผลหลังแก้คิวพิมพ์ |
| --- | --- | --- |
| บันทึกรูปแล้ว แต่ยังไม่เพิ่มรูปเข้ารอบถ่าย | รูปยังอ่านได้ แต่ไม่ผูกกับรอบ | ยังไม่ผ่าน ต้องแก้ในชุด B |
| เพิ่มรูปเข้ารอบแล้ว | รูปและความสัมพันธ์ยังอยู่ รอบเป็น interrupted | ผ่าน |
| รอบเข้าสู่ review แล้ว | รูปและความสัมพันธ์ยังอยู่ รอบเป็น review | ผ่าน |
| งานอยู่ระหว่างส่งพิมพ์ | กลับเป็น pending | เปลี่ยนเป็น needs-review ไม่เข้าเงื่อนไขส่งซ้ำอัตโนมัติ |

ก่อนแก้พบ 2 เกณฑ์ไม่ผ่าน หลังแก้เหลือ 1 เกณฑ์ไม่ผ่าน การตรวจกลับด้วย exit code **2** หมายถึงยังมีช่องว่างตามเกณฑ์ ไม่ใช่ผลผ่านทั้งหมด หลักฐานเครื่องนี้อยู่ใน `output/desktop-reliability-baseline.json` และ `output/desktop-reliability-after-print-fix.json`

ตรวจ source ผู้เรียกแล้ว: `drainPrintQueue()` เลือกงาน pending และ `koko:print-jobs` เรียก drain เมื่อโหลดรายการ จึงยกระดับงานป้องกันส่งซ้ำให้ทำก่อน แม้เดิมคิวพิมพ์อยู่ระยะ 3

## ลำดับงานและเกณฑ์รับ

| ลำดับ | งาน | เกณฑ์ผ่าน | สถานะ |
| --- | --- | --- | --- |
| A | หยุดการส่งซ้ำของงานพิมพ์ที่ไม่ทราบผล | เปิดใหม่แล้วยังรอตรวจ; ส่งซ้ำเฉพาะผู้ใช้เลือก; ปฏิเสธส่งซ้ำได้; รูปและจำนวนสำเนาเดิมอยู่ครบ | แก้ source และทดสอบ service แล้ว; ยังไม่ตรวจ UI/Electron จริง |
| B | ทำการบันทึกสื่อและผูกเข้ารอบถ่ายให้กู้ต่อได้ | หยุด process ทุกจุดสำคัญแล้วสื่อไม่สูญหาย/ไม่ผูกผิดรอบ/ไม่สร้างซ้ำ; retry และ recovery ซ้ำได้ | งานพัฒนาถัดไป |
| C | ทดสอบสำรองและกู้คืนข้อมูล | คืนภาพ ประวัติรอบ เทมเพลต และการตั้งค่าในพื้นที่ทดสอบได้ตรงชุด; ตรวจ hash และความสัมพันธ์ | มีคู่มือแล้ว ยังไม่ทดสอบ restore จริง |
| D | ตรวจเต็มระบบและสร้าง candidate เลขใหม่ | Typecheck/ชุดหลักผ่าน; baseline ช่องว่างที่อยู่ในขอบเขตเหลือศูนย์; ตรวจ packaged app; มี checksum/revision/ข้อจำกัด | ยังไม่เริ่ม |
| E | ติดตั้งและทดสอบอุปกรณ์เป้าหมาย | License หลังเปิดใหม่ 10 รอบ, กล้อง 100 รอบ/ถอดเสียบ 5 ครั้ง, คิวจำลองครบเส้นทาง 50 งาน/พิมพ์จริง 10 งาน, ใช้ต่อเนื่อง 4 ชั่วโมง | รอข้อมูลอุปกรณ์และผลผู้ใช้ |

### A — ผลงานที่ทำในรอบนี้

- `print-queue.ts`: งาน `printing` ที่พบหลังเปิดใหม่กลายเป็น `needs-review`; รวมคิวเก่าที่เคยกลับเป็น pending พร้อมข้อความ interrupted ของรุ่นก่อนด้วย
- เพิ่มการ retry/cancel ที่ตรวจสถานะใน store และให้ Main เรียกใช้ งาน submitted/simulated/cancelled ไม่ถูกย้อนกลับเป็น pending ผ่านการ retry นี้
- UI แสดงสถานะภาษาไทย/อังกฤษ ปุ่ม **ตรวจแล้ว ส่งพิมพ์อีกครั้ง** มีคำยืนยันให้ตรวจเครื่องพิมพ์และคิว Windows ก่อนส่งซ้ำ หรือเลือก **ไม่ส่งซ้ำ**
- ระบุว่าการยกเลิกในแอปไม่ได้ถอนงานที่ Windows รับไปแล้ว และ submitted ไม่ได้ยืนยันว่ากระดาษออกมาแล้ว
- แก้ shared contract ให้รองรับทั้ง simulated และ needs-review
- Typecheck ผ่าน; `test:print-queue` **7/7 ผ่าน** รวม reopen ซ้ำ, retry/cancel, คิวเก่า และการเก็บ 50 งาน/หลายสำเนา การจำลองนี้ตรวจ store เท่านั้น ยังไม่ใช่เกณฑ์คิวจำลองครบ UI → Main → spooler

การแก้ A อยู่ใน working tree ของ `D:\pKOKO` เท่านั้น **installer 0.1.29 ที่สร้างก่อนหน้านี้ยังไม่มีการแก้ A** และยังมีพฤติกรรมเดิม ไม่ได้สร้างหรือแจก installer รุ่นใหม่ในรอบนี้

### B — แผนแก้ความสัมพันธ์สื่อกับรอบถ่าย

1. แยกขั้นตอนบันทึกสื่อ/เพิ่มเข้ารอบ/ตอบกลับ UI ให้มีตัวประสานงานใน Main ที่ทดสอบได้ ครอบคลุมภาพต้นฉบับ วิดีโอ และภาพประกอบจากเทมเพลต
2. บันทึกข้อมูลการเขียนที่ยังไม่จบลงดิสก์ก่อนเริ่มเขียนสื่อ โดยระบุรอบถ่าย ชนิดสื่อ โฟลเดอร์ปลายทาง และรหัสรายการที่ใช้ซ้ำได้ เพื่อให้รู้ว่าสื่อที่เหลือต้องกลับเข้ารอบใดแม้ process หยุดระหว่างสอง store
3. กู้เฉพาะรายการที่ยืนยันตัวตนไฟล์/ความสมบูรณ์และรอบปลายทางได้ ห้ามเดารอบจากเวลาหรือชื่อไฟล์ ห้ามทำรายการที่เสียหายให้ดูสำเร็จ; เก็บหลักฐานและแสดงทางตรวจไฟล์ที่ยังยืนยันไม่ได้
4. การกู้ซ้ำและส่งคำขอซ้ำต้องไม่สร้างสื่อหรือความสัมพันธ์ซ้ำ และต้องไม่เปลี่ยนรอบที่ยกเลิก/ถ่ายใหม่กลับเป็นรอบพร้อมส่ง Cloud โดยอัตโนมัติ
5. เพิ่ม test ผ่านตัวประสานงานจริงที่สร้างขึ้น ไม่ใช้เพียงลำดับเรียกจำลองใน baseline ตรวจหยุด process ก่อน/หลังเขียนไฟล์ หลังลงดัชนี หลังผูกเข้ารอบ และก่อนตอบกลับ UI; เพิ่มดิสก์เต็มในไดรฟ์สื่อและไดรฟ์ app data แยกกัน
6. คง compatibility กับข้อมูลเก่า โดยทดสอบข้อมูลที่ไม่มี metadata ใหม่และบันทึกผลต่อ downgrade ให้ชัดเจน

ชุดแรกของ B: ทำภาพต้นฉบับและกรณี `after-photo-before-session` ให้ผ่านก่อน จากนั้นขยายวิดีโอ/ภาพประกอบ และตรวจ cancel/retry/Cloud ของทุกชนิดสื่อ ก่อนรวมเป็น candidate

### C — สำรองและกู้คืน

- ใช้ fixture แยกที่มีสื่อ รอบถ่าย เทมเพลต และค่าตั้งต้น ปิด process แล้วสำรองโฟลเดอร์สื่อกับ app data เป็นชุดเดียวกัน
- คืนลงโฟลเดอร์ทดสอบอีกชุด ตรวจ hash ทุกไฟล์และจำนวน/รหัสความสัมพันธ์ รวมกรณี backup ไม่ครบหรือเขียนคืนไม่สำเร็จ โดยรักษาต้นฉบับ
- หลังผ่าน fixture จึงทดสอบกับ packaged app บนเครื่องทดสอบ/VM รวมการคืนข้อมูลบนเครื่องเดิมและ License ที่ผูกอุปกรณ์
- ปุ่ม backup/restore ในแอปยังไม่อยู่ในงานชุดนี้; ใช้คู่มือที่ทดสอบแล้วก่อน

### D–E — Candidate และผลใช้งานจริง

- ใช้ **0.1.30 หากยังไม่มีการใช้เลขนี้** หรือเลขถัดไปที่ว่าง เก็บ output แยกจาก 0.1.28/0.1.29 และบันทึก source revision พร้อมรายการเปลี่ยนแปลง/hash
- เก็บผล automated tests, browser component checks, packaged Electron และอุปกรณ์จริงแยกกัน ห้ามใช้ผลกลุ่มหนึ่งแทนอีกกลุ่ม
- ทดสอบหน้าคิว: ยืนยันส่งซ้ำ/ยกเลิกคำยืนยัน/ไม่ส่งซ้ำ และเรียก IPC ซ้ำ ต้องไม่เพิ่มงานซ้ำ การเปิดหน้าคิวเฉย ๆ ต้องไม่ส่งงาน needs-review
- ข้อมูลที่ต้องใช้จากผู้ทดสอบ: ติดตั้งรุ่นใดแล้ว, Windows, รุ่นกล้อง/วิธีเชื่อม, รุ่นเครื่องพิมพ์/driver/กระดาษ และเครื่องหรือ VM ที่ใช้ทดสอบ
- เปิด pilot หลังเกณฑ์เดิมผ่าน ไม่เปิดดาวน์โหลดสาธารณะหรือเปลี่ยนเว็บเพียงเพราะ unit tests ผ่าน

## Compatibility ที่ต้องคุม

คิวที่มีสถานะ `needs-review` อ่านด้วย source รุ่นใหม่นี้ได้ แต่ validator ของ **0.1.29 ไม่รองรับสถานะนี้** จึงห้ามอ้างว่าย้อนรุ่นได้ด้วยการรัน installer เก่าอย่างเดียว ต้องสำรองข้อมูลก่อนทดสอบ และตรวจแนวทางคืนข้อมูล/แปลงคิวก่อนเสนอ downgrade โดยไม่เปลี่ยนงานที่ไม่ทราบผลเป็น pending

## คำสั่งตรวจ baseline ซ้ำ

```powershell
& 'C:\Program Files\nodejs\node.exe' scripts/studio-desktop-reliability-check.cjs D:\pKOKO output/desktop-reliability-current.json
```

Exit 0 = เกณฑ์ที่สคริปต์ครอบคลุมผ่าน, 2 = พบช่องว่างของพฤติกรรม, 1 = สคริปต์ทำงานผิดพลาด ผลตรวจนี้ไม่จำลองไฟดับระดับ OS/ดิสก์ และไม่ใช่การทดสอบภาพ JPEG decoder หรือฮาร์ดแวร์จริง
