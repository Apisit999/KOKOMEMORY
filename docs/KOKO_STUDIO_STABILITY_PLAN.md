จุดกลับมาทำต่อล่าสุด: [KOKO_STUDIO_RESUME_CHECKPOINT.md](KOKO_STUDIO_RESUME_CHECKPOINT.md) — 14 ตุลาคม: งานพื้นที่ว่างระยะ 2 เชื่อม Main/UI และทดสอบแล้ว สร้าง staging 0.1.29; ยังต้องทดสอบแอปที่ติดตั้งจริงและฮาร์ดแวร์ ดู [ผลและคู่มือรอบนี้](KOKO_STUDIO_STORAGE_2026-10-14.md)

## หลักฐานตั้งต้น

- เปิดภาพ `Screenshot 2026-10-13 194209.png` แล้ว: Desktop แสดง `active`, “License ใช้งานได้” และ “เชื่อมอุปกรณ์กับบัญชีเรียบร้อยแล้ว” ถือเป็นหลักฐานว่าเส้นทางเชื่อมบัญชีสำเร็จในการใช้งานครั้งนี้
- ยังไม่มีหลักฐานรอบนี้ว่าเปิดแอปใหม่แล้วสถานะคงอยู่ หรือทำงานกับกล้อง/เครื่องพิมพ์จริงได้ต่อเนื่อง
- แผนเดิมบันทึกว่ามี staging installer 0.1.27 แยกพื้นที่ข้อมูลแล้ว และ typecheck กับ license-runtime 7/7 ผ่านในรอบก่อน ผลนี้ไม่ใช่ผลการรันทดสอบใหม่

- `account-link-card.tsx` หยุดรอเมื่อ polling เกิด exception และเรียก cancel ใน effect cleanup เป็นจุดตรวจการหลุดของเครือข่าย การเปลี่ยนหน้า และการเปลี่ยน callback ก่อนสรุปว่าเป็นบั๊ก
- `print-queue.ts` บันทึกไฟล์แบบเขียนชั่วคราวแล้ว rename และเปลี่ยนงานที่ค้าง `printing` กลับเป็น `pending` เมื่อเปิดใหม่ ต้องตรวจเส้นทางผู้เรียกต่อเพื่อป้องกันการส่งพิมพ์ซ้ำในกรณีไม่ทราบว่าปริ้นเตอร์รับงานแล้วหรือยัง
- มีชุดทดสอบ storage, capture-session, camera, license, template และ print-queue ใน package scripts แล้ว รอบนี้ยังไม่ได้รันหรือยืนยันผลของชุดเหล่านี้

## เป้าหมายก่อนเปิดให้ทดลองใช้งานจริง

ผู้ใช้ติดตั้ง เปิดแอป เชื่อมบัญชี ถ่ายภาพ จัดเทมเพลต บันทึก และพิมพ์ได้ครบ เมื่อเน็ตหรืออุปกรณ์หลุดต้องทราบสาเหตุและกลับมาทำงานต่อได้ รูปที่บันทึกสำเร็จแล้วต้องอยู่ครบ

ตัวเลขด้านล่างเป็นเกณฑ์รับงานที่เสนอ ไม่ใช่ผลทดสอบที่ทำแล้ว ต้องบันทึกรุ่นแอป Windows กล้อง ไดรเวอร์ เครื่องพิมพ์ และชุดข้อมูลที่ใช้ทุกครั้ง

## ลำดับดำเนินงาน

### ระยะ 1 — บัญชีและ License (เร่งด่วน)

งาน:
- ตรวจ lifecycle ของการเริ่ม รอผล ยกเลิก หมดเวลา และอนุมัติ ป้องกันการ polling ซ้อนและผลเก่าทับคำขอใหม่
- แยก error ชั่วคราว เช่น network/timeout/5xx ออกจากรหัสหมดอายุหรือถูกปฏิเสธ ให้ลองใหม่แบบจำกัดจำนวน/เวลาและเคารพ Retry-After โดยไม่เริ่มรหัสใหม่ทุกครั้งที่เน็ตสะดุด
- ตรวจการบันทึกสิทธิ์และสถานะบัญชีหลังปิดเปิดแอป ให้ UI อ่านสถานะที่เชื่อถือได้แทนการจำเฉพาะในหน้าจอ
- แสดงอายุรหัส เวลาใช้งานออฟไลน์ และวิธีแก้ไขเป็นภาษาไทยและเวลาไทย ลดข้อความทางเทคนิคในหน้าผู้ใช้
- ตรวจว่าการรับ Free ซ้ำหรือคำขออนุมัติซ้ำไม่สร้างสิทธิ์หรืออุปกรณ์ซ้ำ ตรวจเจ้าของบัญชีและการใช้รหัสซ้ำฝั่ง API

เกณฑ์ผ่าน:
- ติดตั้งและเชื่อมบัญชีครบเส้นทางบน staging ได้; ปิดเปิดแอป 10 รอบยังได้บัญชี/สิทธิ์ที่ถูกต้อง
- กรณีเน็ตหลุดระหว่างรอผล รหัสหมดอายุ ยกเลิก ใช้ซ้ำ และสลับหน้า มีผลลัพธ์ชัดเจน ไม่มีการรอค้าง
- ใช้งานออฟไลน์ได้เฉพาะภายในช่วงสิทธิ์ที่เซิร์ฟเวอร์ลงนาม เมื่อพ้นช่วงต้องอธิบายการเชื่อมต่อใหม่; ทดสอบเวลาโดยใช้ clock จำลองในชุดทดสอบ

### ระยะ 2 — รูป รอบถ่าย และกล้อง (เร่งด่วน)

งาน:
- ตรวจการบันทึกรูปและรายการรอบถ่ายให้สอดคล้องกันเมื่อเขียนไฟล์ไม่สำเร็จ แอปปิดกะทันหัน หรือดิสก์เต็ม
- แสดงว่าบันทึกสำเร็จต่อเมื่อข้อมูลจำเป็นบันทึกครบ; มีทางกู้รูปหรือรายการที่ค้างโดยไม่เขียนทับข้อมูลเดิม
- ตรวจปุ่มถ่ายซ้ำระหว่างกำลังทำงาน การถอดเสียบกล้อง และการคืนทรัพยากร preview เมื่อเปลี่ยนหน้า
- เพิ่มขั้นตอนสำรอง/กู้คืนข้อมูล และตรวจพื้นที่ว่างก่อนเริ่มงาน

เกณฑ์ผ่าน:
- ถ่ายและบันทึกอย่างน้อย 100 รอบด้วยอุปกรณ์เป้าหมาย เปิดรูปที่บันทึกสำเร็จได้ครบ ไม่มีรายการสำเร็จหลอกหรือการบันทึกซ้ำจากการกดรัว
- จำลองหยุดแอประหว่างบันทึกและพื้นที่ไม่พอด้วยข้อมูลทดสอบ แล้วเปิดใหม่ได้พร้อมคำแนะนำกู้คืน
- ถอดเสียบกล้องซ้ำ 5 ครั้ง กลับมาถ่ายได้โดยไม่ต้องติดตั้งโปรแกรมใหม่

### ระยะ 3 — คิวพิมพ์และเทมเพลต (เร่งด่วน)

งาน:
- ตรวจวงจรคิวตั้งแต่สร้างภาพ ส่งเข้า Windows spooler จนกลับมาเปิดแอปใหม่
- แสดงความต่างระหว่าง “ส่งเข้าคิวแล้ว” กับ “พิมพ์ออกมาแล้ว” ตามข้อมูลที่ระบบตรวจได้จริง
- งานที่ไม่แน่ใจว่าเครื่องพิมพ์รับแล้วหรือยังต้องให้ผู้ใช้ตรวจและเลือกพิมพ์ใหม่ ป้องกันการส่งซ้ำอัตโนมัติ
- ตรวจเครื่องพิมพ์ offline กระดาษหมด ยกเลิกงาน จำนวนสำเนา และคิวเต็ม พร้อมทางจัดการประวัติเก่า
- ตรวจขนาดภาพ ระยะขอบ แนวกระดาษ และตำแหน่งตัดกับกระดาษและไดรเวอร์เป้าหมาย

เกณฑ์ผ่าน:
- ทดสอบคิวอย่างน้อย 50 งานในโหมดจำลอง และอย่างน้อย 10 งานพิมพ์จริง รวมหลายสำเนา
- หยุดแอประหว่างส่งพิมพ์แล้วเปิดใหม่ งานยังตรวจสอบได้และไม่พิมพ์ซ้ำเอง
- รูปต้นฉบับยังอยู่แม้การพิมพ์ล้มเหลว; ผลจำลองและผลพิมพ์จริงบันทึกแยกกัน

### ระยะ 4 — ตรวจปัญหาและทดสอบก่อนออกรุ่น

เริ่มงานบันทึกข้อผิดพลาดตั้งแต่ระยะ 1 เพื่อใช้วิเคราะห์ตลอดโครงการ แล้วรวมเกณฑ์ออกรุ่นในระยะนี้

งาน:
- บันทึกเวอร์ชัน เวลา ขั้นตอน และรหัสเหตุการณ์ของข้อผิดพลาด พร้อมปุ่มส่งออกข้อมูลวิเคราะห์ที่ไม่รวม token, License key, รหัสเชื่อมบัญชี หรือรูปผู้ใช้โดยปริยาย
- ติดตาม error/latency ของ API และ health/readiness พร้อมเกณฑ์แจ้งเตือนจากค่าพื้นฐานที่วัดได้
- ให้ CI รัน typecheck และชุดทดสอบที่เกี่ยวข้องกับส่วนที่แก้; ก่อน release รันชุดสำคัญครบและตรวจ packaged app
- ทดสอบติดตั้งใหม่ อัปเกรด และกู้คืนบนเครื่องทดสอบ/VM ให้รูป เทมเพลต และสิทธิ์คงอยู่
- กำหนดเวอร์ชัน candidate ไม่ซ้ำ บันทึก source revision/configuration/checksum และแผนกลับรุ่น รวมข้อจำกัดของการย้อน schema
- เตรียม code signing และข้อมูลดาวน์โหลดให้ตรงกับ installer ก่อนเปิดสาธารณะ

เกณฑ์ผ่าน:
- เปิดใช้งานต่อเนื่องอย่างน้อย 4 ชั่วโมงพร้อมถ่าย/บันทึก/พิมพ์ตามรอบ ไม่มี crash หรือข้อมูลสูญหาย; วัดหน่วยความจำว่ากลับใกล้ค่าหลัง warm-up เมื่อจบรอบงานและไม่มีแนวโน้มโตไม่หยุด
- ติดตั้งใหม่และอัปเกรดผ่านบนเครื่องหลักและเครื่องทดสอบอีก 1 เครื่อง โดยเปิดจาก shortcut ได้
- มีรายงานผล คู่มือกู้คืน และรายการข้อจำกัดที่ทำซ้ำตรวจสอบได้

### ระยะ 5 — ทดลองใช้งานกลุ่มเล็ก

- เริ่มกับ 3–5 เครื่อง/ผู้ทดสอบที่ใช้ชุดอุปกรณ์ซึ่งผ่านการตรวจแล้ว เก็บข้อมูลอย่างน้อย 1 งานจำลองเต็มกระบวนการต่อเครื่อง และงานนำร่องที่มีผู้ดูแล
- ติดตามความสำเร็จของการถ่าย บันทึก ส่งพิมพ์ และการเชื่อมบัญชี พร้อมจำนวน crash และเวลาที่ใช้แก้ปัญหา
- ข้อผิดพลาดทำให้รูปสูญหาย สิทธิ์ผิดบัญชี แอปเปิดไม่ได้ หรือพิมพ์ซ้ำเอง ถือเป็นเหตุหยุดขยายผู้ใช้และแก้ก่อน
- เปิดดาวน์โหลดวงกว้างเมื่อเกณฑ์ระยะ 1–4 และผลนำร่องผ่าน ไม่มีปัญหาสำคัญค้าง พร้อมวิธีช่วยเหลือและกลับรุ่น

## งานชุดแรกเมื่อเริ่มพัฒนา

1. ทบทวน diff เดิมและบันทึก baseline ของสอง repository โดยรักษางานที่ยังไม่ commit
2. ตรวจและแก้ polling/lifecycle ของ account linking พร้อมการกลับมาทำงานเมื่อเครือข่ายสะดุด
3. ทำสถานะบัญชี/License หลังเปิดแอปใหม่ให้ชัดเจน และเติมการทดสอบกรณีผิดพลาดที่จำเป็น
4. สร้าง staging candidate เวอร์ชันใหม่ พร้อมรายการตรวจ 10 รอบเปิดแอปและสถานการณ์เน็ตหลุด
5. เมื่อผ่านจึงทำระยะรูป/กล้องและคิวพิมพ์ตามลำดับ

ผู้พัฒนารับผิดชอบโค้ด การทดสอบอัตโนมัติ และแพ็กเกจ; เจ้าของทดสอบ Google login กับอุปกรณ์จริงและยืนยันภาพ/งานพิมพ์ ต้องเก็บรุ่นกล้อง เครื่องพิมพ์ ไดรเวอร์ Windows และกระดาษก่อนการทดสอบฮาร์ดแวร์ ระยะเวลาแต่ละช่วงประเมินหลังตรวจ baseline และอุปกรณ์ โดยตัดสินจากเกณฑ์ผ่าน ไม่ใช้จำนวนวันแทนผลทดสอบ

รอบจัดแผนนี้อ่านเอกสาร source บางส่วน และภาพหน้าจอแล้ว ยังไม่ได้แก้พฤติกรรมแอป รันทดสอบใหม่ หรือ deploy
