# ทดสอบโหลด — ระบบส่งรูป (M5) — 19 พฤศจิกายน 2026

เป้าหมายตาม Master Prompt หัวข้อ 10: หน้า Session โหลดรูปแรก **p95 < 3 วินาที** บน 4G, อัปโหลดสำเร็จ **≥ 99.5%**, จำลองงาน 1,000 แขก + คนสแกนพร้อมกันท้ายงาน + หลายบูธอัปโหลดพร้อมกัน

> **อ่านก่อน:** ทดสอบบนเครื่องพัฒนาเครื่องเดียว (ไม่ใช่เซิร์ฟเวอร์จริง) ตัวเลขจึงบอก **ลำดับความสำคัญและคอขวด** ไม่ใช่สเปกที่รับประกันบน Hostinger/Cloudflare R2 ยังไม่ได้ทดสอบกับ 4G จริง และยังไม่ได้ทดสอบบน staging

ในชุดทดสอบเต็ม (แขก 1,000 คน, 100 คนต่อ IP): **ก่อนแก้เปิดหน้าได้เพียง 23%** (503 ถึง 766 จาก 1,000) **หลังแก้ 100%**

**แก้แล้ว:** `share/view` และ `share/photo` นับในหน่วยความจำของโปรเซส (`src/lib/studio/memory-rate-limit.ts`) แทนธุรกรรมฐานข้อมูล ส่วน `share/code` และ `account/link` (เดาได้/อ่อนไหว) ยังใช้ตัวจำกัดเดิมในฐานข้อมูล ข้อแลกเปลี่ยนที่ตั้งใจ: ตัวนับหายเมื่อรีสตาร์ต และถ้ารันหลายอินสแตนซ์แต่ละตัวนับแยกกัน

### 3. แขก 1,000 คน (แต่ละคนเปิดลิงก์ + กดดูรูป 2 ครั้ง), ตัวสร้างโหลดแก้แล้ว

| สถานการณ์ | เปิดสำเร็จ | ทำครบ | view p50 / p95 / p99 | รูปแรก p95 |
|---|---|---|---|---|
| A กระจายใน 60 วินาที, IP คนละตัว | 100% | 100% | 207 / 375 / 486 ms | 421 ms |
| B กระจายใน 60 วินาที, 100 คนต่อ IP | 100% | 100% | 194 / 325 / 376 ms | 385 ms |
| C **ทุกคนพร้อมกันภายใน 5 วินาที** | 100% | **76.8%** | 4,892 / 9,197 / 9,228 ms | 17.9 วินาที |

- A และ B ผ่านเป้า "รูปแรก < 3 วินาที" ฝั่งเซิร์ฟเวอร์สบาย (0.4 วินาที) ยังไม่รวมเวลาส่งข้อมูลผ่าน 4G จริง
- C เกินความจุของโปรเซสเดียว (ราว 600 คำขอ/วินาทีช่วงสั้น ๆ เทียบความจุ ~200) ผลคือช้า และคำขอกดดูรูป 238 จาก 2,000 ล้มเหลวที่ระดับการเชื่อมต่อ

### 4. หลายบูธอัปโหลดพร้อมกัน

5 บูธ × 10 รอบ × 3 รูป (รูปละ 2.3 MB), แต่ละบูธมี IP ของตัวเอง

- รอบอัปโหลดสำเร็จ **50/50 (100%)**, ทุกคำขอ 500 ครั้งตอบ 200 (ยังไม่ได้ทดสอบกับเครือข่ายที่หลุดกลางทาง จึงยังไม่วัดผลของการลองซ้ำ)
- รวมประมาณ **110–126 รูป/นาที** (≈ 22–25 รูป/นาที/บูธ)
- ขั้น "ยืนยันรูป" ใช้ ~1.4 วินาทีต่อรูปเมื่อมีงานเดียว และ **p95 3.8–4.3 วินาที** เมื่ออัปโหลดพร้อมกัน 8 ทาง เพราะเซิร์ฟเวอร์ย่อรูปก่อนตอบ (ใช้ CPU)
- **การอัปโหลดไม่ทำให้แขกช้า:** แขกเปิดลิงก์ระหว่างบูธอัปโหลด p95 144 ms เทียบ 146 ms ตอนไม่มีใครอัปโหลด

## ข้อผิดพลาดของการวัดที่แก้ระหว่างทาง

รอบแรกตัวสร้างโหลดอ่านภาพย่อเป็นข้อความ (`response.text()`) ทำให้ CPU ตัวสร้างโหลดเต็มและบวกเวลาเข้าทุกการวัด ตัวเลขรอบนั้น (แขก p50 1.3–2 วินาที) จึง **สูงเกินจริง** และไม่ควรใช้ ตัวเลขในรายงานนี้มาจากรอบหลังแก้ (นับขนาดภาพโดยไม่ถอดรหัส) ยกเว้นผลของข้อ 2 ที่เป็นความล้มเหลวฝั่งเซิร์ฟเวอร์จริง (503)

## ข้อเสนอแนะ

1. **ตั้งค่า `STUDIO_TRUSTED_CLIENT_IP_HEADER` ทุกสภาพแวดล้อม** ถ้าไม่ตั้ง ทุกคนนับเป็นผู้เรียกคนเดียว (staging ตั้งไว้แล้ว)
2. **ท้ายงานที่คนสแกนพร้อมกันเป็นพัน** ต้องการมากกว่า 1 โปรเซส (เช่น หลายโปรเซส/อินสแตนซ์หลัง nginx) หรือแคชผลหน้าแชร์สั้น ๆ ถ้าใช้หลายอินสแตนซ์ ควรเปลี่ยนตัวนับในหน่วยความจำเป็นตัวนับกลาง (เช่น Redis) หรือจำกัดที่ nginx
3. **การย่อรูปตอนยืนยัน** กิน CPU ถ้าเพิ่มจำนวนบูธมาก ควรย้ายไปทำเบื้องหลัง (คิว/worker) ไม่ให้แย่งกับการเปิดหน้าของแขก
4. **ทดสอบซ้ำบน staging** (Hostinger + R2 จริง + Firestore จริง) พร้อมวัดผ่านเครือข่าย 4G จริงก่อนอ้างตัวเลขกับลูกค้า
5. ยังไม่ได้ทดสอบ: ผลของการลองอัปโหลดซ้ำเมื่อเน็ตหลุด, งานยาวหลายชั่วโมง, หน่วยความจำของเซิร์ฟเวอร์ตลอดงาน, ค่าใช้จ่ายต่องาน (Storage + Bandwidth)
