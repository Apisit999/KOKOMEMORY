# KOKO Memory — แผนปรับดีไซน์ทั้งเว็บไซต์

เอกสารนี้ขยายแผน creative-studio-roadmap.md ให้ครอบคลุมเว็บไซต์ทั้งหมด เป็นแผนออกแบบและลำดับพัฒนา ไม่ใช่รายการฟีเจอร์ที่เสร็จแล้ว

## 1. เป้าหมาย

ให้ผู้เข้าชมเข้าใจในหน้าแรกว่า KOKO ให้บริการเช่า Photobooth ขายโปรแกรม Photobooth ซอฟต์แวร์ธุรกิจ และงานออกแบบ/พิมพ์ 3D เลือกบริการได้เร็ว เห็นผลงานจริง และทำรายการต่อได้ทั้งมือถือและคอมพิวเตอร์

แบรนด์ร่วม: KOKO Memory / Creative Technology Studio — “จากโมเมนต์ที่อยากเก็บ สู่สิ่งใหม่ที่อยากสร้าง” ชื่อบริการและคำอธิบายภาษาไทยต้องเด่นกว่าคำตกแต่งภาษาอังกฤษ

ผลลัพธ์ที่ต้องได้: ดีไซน์ต่อเนื่องทุกหน้า มีภาพและวิดีโอที่สื่อถึงบริการ มีแอนิเมชันที่ควบคุมได้ และมีสถานะ/ข้อความบอกลูกค้าชัดเจนว่าต้องทำอะไรต่อ

## 2. สิ่งที่พบในโค้ดปัจจุบัน

- หน้าแรกและ /services มีต้นแบบ StudioExperience แล้ว แต่ใช้โครงสร้างเกือบเหมือนกัน ต้องแยกหน้าที่สองหน้าให้ชัด
- /software และ /software/photobooth เป็นหน้ารับสอบถาม ยังไม่มีสินค้า ราคา หรือระบบส่งมอบซอฟต์แวร์
- /enquiry เตรียมอีเมลในโปรแกรมอีเมลของผู้ใช้ ไม่มีการส่งหรือบันทึก lead บนเซิร์ฟเวอร์
- /packages เป็นหน้าดูแพ็กเกจสาธารณะ ใช้ข้อมูลร่วมกับระบบจอง แต่ CTA ใหม่บางจุดเชื่อม /booking/package ซึ่งถูกตรวจล็อกอินและอีเมลที่ยืนยันแล้วโดย booking layout
- ส่วนสาธารณะ บัญชีลูกค้า จอง และหลังบ้านมี layout และแนวทางสีหลายรูปแบบ ต้องทำมาตรฐานร่วม
- มี gallery งานจริง สินค้า/ใบเสนอราคา/คำสั่งซื้อ 3D และระบบจองอยู่แล้ว ให้ปรับ UI ครอบระบบเหล่านี้
- /search เปิดด้วย feature flag; /dashboard เป็นหน้าเปล่าตามโค้ดที่อ่าน ส่วน /users /reports /settings /payments และหน้าทดสอบต้องตรวจผู้เรียกใช้และสิทธิ์ก่อนจัดเมนูหรือ redirect
- ตรวจโครงสร้างจากไฟล์แล้ว แต่ยังไม่ได้ตรวจหน้าจอจริงครบทุกเส้นทาง

## 3. แนวทางดีไซน์: Creative Studio + Product Showroom

ใช้ภาพถ่ายขนาดใหญ่ กริดที่มีจังหวะ ภาพพิมพ์วางซ้อน ตัวอักษรไทยอ่านง่าย และพื้นสีถ่านสลับครีม เพื่อให้หน้าเว็บมีทั้งความสร้างสรรค์และข้อมูลที่อ่านสะดวก

เอกลักษณ์หลัก 3 อย่าง: รูปทรงกรอบภาพพิมพ์, เส้นหรือกริดที่สื่อถึงการสร้างชิ้นงาน, เครื่องหมายดอกจันของแบรนด์ ใช้องค์ประกอบเหล่านี้ซ้ำอย่างพอดี หน้าโปรแกรมเน้นหน้าจอจริง หน้า 3D เน้นวัตถุจริง หน้าเช่าเน้นบรรยากาศคนใช้งาน

## 4. เมนูและโครงสร้างข้อมูล

เมนู desktop: บริการ (4 หมวด) / ผลงาน / เกี่ยวกับเรา / ติดต่อ + บัญชี + ปุ่ม “เลือกบริการ” เมนู mobile เป็น drawer แสดง 4 บริการชัดเจน มีปุ่มปิด focus trap ปิดด้วย Escape และคืน focus ไปปุ่มเปิด

บริการ 4 หมวดเชื่อมไป /photobooth (หน้าใหม่), /software/photobooth, /3d-printing, /software บนหน้าบริการเฉพาะใช้ CTA ตามงาน เช่น ดูแพ็กเกจ / ขอรายละเอียดโปรแกรม / ส่งไฟล์ประเมินราคา

Footer กลาง: บริการทั้งหมด ช่องทางติดต่อ บัญชี และลิงก์เอกสารการใช้บริการเมื่อจัดทำแล้ว ซ่อนรายการที่ยังไม่มีปลายทางจริง

เส้นทางดูข้อมูลต้องเปิดสาธารณะ การจอง/ทำรายการใช้ auth ตามระบบที่ออกแบบและส่งผู้ใช้กลับจุดเดิมหลังล็อกอิน หลีกเลี่ยงให้ผู้ใช้เสียบริการหรือรายการที่เลือกไว้

## 6. หน้าแรกที่ต้องการ

ลำดับบน desktop และ mobile:

1. Header: โลโก้ เมนูบริการ บัญชี และช่องทางเริ่มต้น
2. Hero: “ไอเดียของคุณ มีชีวิตได้” + อธิบาย 4 บริการในข้อความที่มองเห็นทันที + คอลลาจภาพ/หน้าจอ/ชิ้นงาน 3D พร้อมปุ่มเลือกบริการ
3. Service chooser: 4 การ์ดมีชื่อไทย ประโยชน์หลัก และภาพตรงบริการ; บนมือถือเรียงลำดับอ่านได้โดยไม่ต้องปัดหา
4. Selected work: ผลงานจริง 3–6 งาน เลือกหมวดและดูต่อได้ ถ้ายังไม่มีผลงานบางหมวดให้ใช้เนื้อหาอธิบายตรงไปตรงมา
5. Motion showcase: คลิปสั้นจากงานจริง กดเล่น/หยุดได้ มีภาพปกและคำบรรยายเมื่อมีเสียงพูด
6. วิธีเริ่มงาน 3 ขั้น: เลือกบริการ → ส่งรายละเอียด → ยืนยันขอบเขตและราคา
7. รีวิวจากข้อมูลจริง + FAQ ที่เกี่ยวกับการเลือกบริการ
8. CTA ติดต่อ และ footer กลาง

ความแตกต่างระหว่างหน้าแรกกับ services: หน้าแรกสร้างความเข้าใจแบรนด์และความสนใจ ส่วน services ช่วยเทียบและเลือกบริการ รายละเอียดไม่ควรซ้ำกันทั้งหน้า

## 7. การจองและชำระเงิน

ครอบคลุม /booking, /booking/package, /booking/customer, /booking/schedule, /booking/review, /booking/payment, /booking/success รวม /payments ถ้ายังอยู่ในเส้นทางที่ใช้จริง

- แสดงความคืบหน้าเป็นขั้นตอนสั้น ๆ และสรุปรายการด้านข้าง desktop / ย่อขยายได้บนมือถือ
- แสดงชื่อแพ็กเกจ ราคา ค่าระยะทาง/เพิ่มเติม ยอดที่ต้องชำระ และเหตุผลของยอดรวมก่อนยืนยัน
- ฟอร์มใช้ label ชัด ตัวอย่างข้อมูลถูกต้อง validation ใต้ช่อง และสรุปข้อผิดพลาดพร้อมพา focus ไปช่องที่ต้องแก้
- กลับขั้นก่อนหน้าโดยไม่ล้างข้อมูล แสดงสถานะกำลังส่งและป้องกันการกดซ้ำฝั่ง UI พร้อมตรวจซ้ำฝั่ง server ตามธุรกรรมเดิม
- แสดงตัวอย่างสลิป สถานะอัปโหลด และข้อความรอตรวจ การส่งสลิปสำเร็จต้องแยกจากการอนุมัติรับเงิน
- หน้าสำเร็จสรุปเลขอ้างอิง วัน/สถานที่ สถานะปัจจุบัน และสิ่งที่ต้องทำต่อ เชื่อมบัญชีลูกค้า
- รักษา state และ redirect หลัง login; ตรวจ /packages → เลือกแพ็กเกจ → login → กลับมาจองด้วยแพ็กเกจที่เลือก

## 8. บัญชีลูกค้า

ครอบคลุม /account, /account/login, /account/register, /account/forgot-password, /account/profile, /account/security, /account/bookings และรายละเอียด, /account/3d-printing รวม quotes/new/รายละเอียด และ orders/รายละเอียด

- หน้า login/register ใช้ภาพฝั่งเดียวกับฟอร์มที่อ่านง่าย มือถือย่อภาพ ลดสิ่งรบกวน และแจ้งขั้นตอนยืนยันอีเมลชัดเจน
- Dashboard แสดง “สิ่งที่ต้องทำต่อ” ก่อนสถิติ เช่น ยืนยันใบเสนอราคา ส่งสลิป หรือรอทีมตรวจ
- การจองและงาน 3D ใช้การ์ด/ตารางกลาง ระบุสถานะ วันที่และเลขอ้างอิง ค้นหา/กรองเมื่อมีรายการมาก
- หน้ารายละเอียดใช้ timeline + สรุปรายการ + เอกสาร/ไฟล์ + การกระทำที่ใช้ได้ตามสถานะ
- ใบเสนอราคา 3D เน้นขนาด หน่วย วัสดุ จำนวน และไฟล์ พร้อมแสดงชื่อและสถานะอัปโหลด
- ส่วน “ซอฟต์แวร์ของฉัน” ออกแบบไว้ในระยะระบบขาย หลังมีข้อมูลคำสั่งซื้อและไลเซนส์จริงจึงเปิดเมนู

## 9. หลังบ้าน

ครอบคลุม /admin/login, dashboard, bookings, payments, gallery, portfolio/categories, reviews, settings และ /admin/3d-printing ทั้ง products/quotes/orders/payments รวมหน้าสร้างและรายละเอียด

- Sidebar กลุ่มงาน: ภาพรวม / Photobooth / 3D Print / เนื้อหาและผลงาน / ตั้งค่า; สอบถามและซอฟต์แวร์เพิ่มเมื่อระบบพร้อม
- ตารางใช้ toolbar และรูปแบบค้นหา/กรอง/แบ่งหน้าชุดเดียว; บนมือถือดูข้อมูลสำคัญก่อนและเปิดรายละเอียดต่อได้
- หน้ารายละเอียดจัดข้อมูลลูกค้า รายการ ราคา ไฟล์และประวัติสถานะเป็นสัดส่วน; ปุ่มเปลี่ยนสถานะอยู่ตำแหน่งคงที่และชื่อชัด
- การอนุมัติเงิน/ยกเลิก/เปลี่ยนสิทธิ์ต้องใช้การยืนยันตามผลกระทบ พร้อมแสดงเป้าหมายรายการและสถานะล่าสุด
- รักษาสิทธิ์เดิมและตรวจว่า UI ไม่แสดงหรืออนุญาตการทำงานเกินบทบาท
- หน้าเพิ่ม/แก้สินค้าและ portfolio มี preview สื่อ alt และลำดับภาพ; แสดงผลของ draft/published ชัดเจนเมื่อมีระบบรองรับ
- ตรวจหน้า root เก่า /dashboard /users /reports /settings /payments ว่าใครใช้งาน ก่อนย้าย/redirect ป้องกันลิงก์เดิมขาด

## 10. แอนิเมชันและสื่อ

| ตำแหน่ง | ลูกเล่น | พฤติกรรมมือถือ/การเข้าถึง |
| --- | --- | --- |
| Hero | คอลลาจลอย 6–10px ช้า ๆ; optional parallax เล็กน้อยเฉพาะ desktop | มือถือใช้ภาพนิ่งหรือลอยเบา ๆ; มีปุ่มหยุด |
| การ์ดบริการ | ยก 3–4px / ภาพซูมเล็กน้อยเมื่อ hover/focus | กดเข้าหน้ารายละเอียดได้ทันที |
| ผลงาน | reveal opacity/translate ระยะสั้น ครั้งเดียว | เนื้อหาต้องยังปรากฏเมื่อ JS ไม่พร้อม |
| โปรแกรม | วิดีโอสาธิตและสลับภาพหน้าจอตามหัวข้อ | โหลดวิดีโอเมื่อผู้ใช้เลือกเล่น |
| ชิ้นงาน 3D | ภาพหลายมุม; หมุน 3D เมื่อผู้ใช้กดเปิด viewer | มีภาพ fallback; viewer ไม่แย่ง gesture เลื่อนหน้า |
| ฟอร์ม/ตะกร้า | transition สำหรับ error/loading/success | เคารพ reduced motion และแจ้งผ่าน live region |

ใช้ CSS transform/opacity เป็นหลัก หลีกเลี่ยงการเปิดหลายวิดีโอพร้อมกัน หยุดสื่อเมื่อออกจากพื้นที่มองเห็นหรือเปลี่ยนหน้าเมื่อเหมาะสม ไม่ใช้ scroll hijacking หรือ cursor แบบพิเศษที่บดบังปุ่ม

สื่อที่ต้องเตรียมต่อบริการ: ภาพหลักแนวนอน 1 ภาพ, ภาพรายละเอียด 3–6 ภาพ, คลิปสั้น 1 คลิปถ้ามี, คำอธิบายไทย/อังกฤษ โปรแกรมควรมี screen recording จริง และ 3D ควรมีภาพไฟล์คู่ชิ้นงานสำเร็จ

กำหนด poster, alt, สัดส่วนภาพ, จุดโฟกัส และสิทธิ์เผยแพร่ แปลงไฟล์ตามการใช้งานจริงและโหลดภาพนอกจอภายหลัง ไม่ใช้คลิปตัวอย่างที่ทำให้เข้าใจว่าเป็นงานของ KOKO

## 11. งานพื้นฐานในการพัฒนา

1. สร้าง design tokens สำหรับพื้น/ข้อความ/เส้น/ประเภทบริการ/สถานะ ลดการกำหนด hex ซ้ำและแยกสีแบรนด์จากสีสถานะ
2. จัด CSS Studio ที่ปัจจุบันย่อเป็นบรรทัดยาวให้อ่านและบำรุงรักษาง่าย ลด selector global ที่กระทบ navbar หรือหน้าอื่น
3. ทำ PublicShell, TransactionShell, AccountShell, AdminShell ให้ใช้ tokens และ components ร่วมกัน พร้อมกำหนดเจ้าของ header/footer ไม่ซ้ำซ้อน
4. Components กลาง: Button, Field, ServiceCard, MediaCard, StatusBadge, Stepper, SummaryPanel, EmptyState, LoadingState, ErrorState, Dialog และ DataTable ตามความจำเป็นจริง
5. รวมข้อมูลบริการ: id, ชื่อ/คำอธิบายไทยอังกฤษ, สี, media, CTA และปลายทาง เก็บราคา/แพ็กเกจจากแหล่งข้อมูลธุรกิจที่มีอยู่
6. แยก route ใหม่ผ่านโครงสร้างที่ไม่เปลี่ยน URL เดิมโดยไม่ตั้งใจ วาง redirect เฉพาะเส้นทางที่ตรวจแล้ว
7. ใช้ระบบ i18n เดิมผ่าน key สำหรับข้อความใหม่ รวม aria/validation/error; ตรวจ DomTranslator ไม่แก้ข้อความซ้ำหรือทำให้ DOM ไม่ตรง React
8. เพิ่ม metadata รายหน้าและ social preview ตามภาพแบรนด์จริง ตรวจเนื้อหาและ sitemap ถ้ามีการเพิ่ม route

## 12. ลำดับลงมือและผลส่งมอบ

| รอบ | งาน | ผลส่งมอบ/เกณฑ์ผ่าน |
| --- | --- | --- |
| A — ตรวจและกำหนดมาตรฐาน | screenshot inventory, route/auth map, tokens, font, components และ media inventory | รายการหน้าครบ ระบุ baseline และรูปแบบกลางที่นำไปใช้ได้ |
| B — หน้าสาธารณะหลัก | header/footer, home, services, photobooth, packages, software, 3D landing/detail | เลือกบริการและดูข้อมูลได้ก่อนล็อกอิน; หน้าตามแบบทั้ง desktop/mobile |
| C — ผลงานและติดต่อ | portfolio/list/detail, event gallery, about, contact/enquiry, search เมื่อเปิดใช้ | ภาพ/วิดีโอ/การติดต่อทำงานตามสถานะระบบและไม่พาข้ามบริการผิด |
| D — ทำรายการ | login/register/reset, booking ทุกขั้น, payments, account และงาน 3D | เส้นทางทำรายการครบ ข้อมูลไม่หาย และสถานะชัดเจน |

แต่ละรอบเริ่มจากหน้าตัวแทน 1 หน้า แล้วกระจายรูปแบบไปหน้าที่คล้ายกัน ตรวจยืนยันด้วยหน้าจอจริงก่อนขยาย ขอบเขตเวลาขึ้นกับสื่อและข้อมูลที่ได้รับ จึงควรประเมินวันทำงานหลังรอบ A

ระบบรับ lead หลังบ้าน/ระบบขายซอฟต์แวร์เป็นงานเพิ่มจากการเปลี่ยนหน้าตา: enquiries + สถานะติดตาม, products/plans, orders/payments, licences/downloads และ customer software dashboard ใช้แผนเดิมสำหรับรายละเอียด ออกแบบ UI เผื่อได้ แต่เปิดใช้งานหลัง backend และข้อมูลธุรกิจพร้อม

## 13. ตรวจรับ

- ตรวจที่ 360, 390, 768, 1024 และ 1440px รวม landscape และข้อความขยาย 200%; ไม่มีข้อความ/ปุ่มถูกตัดหรือการเลื่อนแนวนอนทั้งหน้า
- keyboard เข้าถึงทุก action, focus มองเห็น, drawer/dialog กักและคืน focus ถูกต้อง, label/error เชื่อมกับ field
- reduced motion ปิดการขยับตามอุปกรณ์ มีปุ่มเล่น/หยุดสื่อและ poster fallback
- ตรวจไทย/อังกฤษทุกหน้า รวมข้อความ error, empty และวัน/จำนวนเงิน
- ตรวจเป้าหมายภาพใหญ่ LCP ≤ 2.5s, CLS ≤ 0.1 และ INP ≤ 200ms จากการวัดจริงเมื่อมีข้อมูล ไม่ถือว่าได้ผลแล้วเพียงเพราะ build ผ่าน
- ตรวจแพ็กเกจสาธารณะ→login→จอง, 3D→quote/order→ชำระ/ติดตาม, portfolio→บริการ, enquiry→ช่องทางส่งจริง
- ตรวจสถานะโหลด/ไม่มีข้อมูล/สิทธิ์ไม่พอ/ไฟล์เสีย/เน็ตขาด; การปิดหรือกลับหน้าต้องไม่สร้างรายการซ้ำ
- ตรวจสิทธิ์และข้อมูลส่วนบุคคลในบัญชี/gallery/admin ตามระบบเดิม
- lint/typecheck/build ผ่าน และบันทึกหน้าที่ตรวจในเบราว์เซอร์กับข้อจำกัดที่ยังเหลือ

## 14. ข้อมูลที่ต้องเติมระหว่างพัฒนา

ภาพ/คลิปจริงทั้ง 4 หมวด, ชื่อและฟีเจอร์โปรแกรม, อุปกรณ์รองรับ, ราคาและสิทธิ์ใช้งาน, เงื่อนไขบริการ/พื้นที่เช่าบูธ, วัสดุและข้อจำกัดงาน 3D, รีวิวที่ได้รับอนุญาต และผู้รับผิดชอบติดตามคำถาม

เริ่มออกแบบและสร้าง components/หน้าได้ก่อน เมื่อข้อมูลสินค้าไม่ครบให้ใช้สถานะรับสอบถามที่ตรงกับความพร้อมจริง และยังไม่แสดงราคา/รีวิว/ตัวเลขความสำเร็จที่ไม่มีหลักฐาน

## ผลการแก้ UI จากการตรวจรอบล่าสุด

- `/packages` ใช้พื้นมืดและการ์ดครีม เพิ่ม metadata เฉพาะหน้าและข้อความแจ้งว่าการจองต้องเข้าสู่ระบบ โดยใช้ข้อมูลราคาและเส้นทางจองเดิม
- CTA เช่าบูธจากหน้า software และ footer หน้าแรกพาไป `/photobooth` เพื่อดูรายละเอียดก่อนเลือกแพ็กเกจ
- Footer กลางใช้พื้นสีถ่านและกล่าวถึงบริการทั้ง 4 กลุ่ม พร้อมใช้อีเมลเดียวกับหน้าติดต่อ
- โลโก้ Navbar ใช้ `fill` พร้อม `sizes`; footer image ใส่ `sizes`; drawer ถูก clip ภายใน overlay เมื่อปิด
- ปรับ accent หน้า 3D และพื้น hero ของ portfolio ให้เข้ากับโทน charcoal/lime/lavender
- หน้า software แสดง Footer กลาง

ตรวจล่าสุด: Playwright หน้า `/packages` แสดง title เฉพาะหน้าและไม่มี console warning/error; ESLint และ `npm run build` ผ่าน ครบ 64 routes

งานตรวจต่อ: ปรับ about/contact และรายละเอียด portfolio/3D ให้ใช้ design system ร่วมกัน ตรวจมือถือหน้า packages/3D/portfolio และลอง flow เลือกแพ็กเกจ → login → กลับมายังรายการที่เลือกด้วยบัญชีทดสอบ
